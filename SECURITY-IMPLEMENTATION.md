## Check 01 — Secret Leak Prevention (Gitleaks)

### 🔍 What We Audited
Scanned the entire codebase for hardcoded secrets — database passwords, JWT signing keys, API tokens — that could leak if the repository went public.

### 🐛 Vulnerabilities Found
- `application.yml` contained a default fallback JWT secret (`404E635266...`) that ships with the binary
- `application-prod.yml` previously allowed default database credentials to propagate to production

### ✅ What We Implemented

**File: `backend/src/main/resources/application.yml`**
```yaml
app:
  jwt:
    secret: ${JWT_SECRET:404E635266...}  # Dev-only default, overridden in prod
```

**File: `backend/src/main/resources/application-prod.yml`**
```yaml
spring:
  datasource:
    url: ${DB_URL}           # Mandatory — no fallback
    username: ${DB_USERNAME} # Mandatory — no fallback
    password: ${DB_PASSWORD} # Mandatory — no fallback

app:
  jwt:
    secret: ${JWT_SECRET}    # Mandatory — no fallback, app won't start without it
```

**File: `README.md`**  
Added a production secret rotation warning notice documenting that operators must set environment variables before deployment.

**File: `.gitignore`**  
Verified exclusion of `.env`, `*.key`, `*.jks`, and credential files.

## Check 02 — Personal Data Flow Audit (Bearer)

### 🔍 What We Audited
Traced every path where PII (passwords, emails, phone numbers) is handled — from request ingestion through logging to database storage — to find data leaks and privacy compliance gaps.

### 🐛 Vulnerabilities Found
1. **Password in Logs**: `LoginRequest.toString()` (auto-generated by Lombok `@Data`) would dump the plaintext password into application logs if any log statement or exception handler serialized the request object
2. **No Data Deletion Capability**: No endpoint existed for users to request deletion of their personal data (GDPR Article 17 / Indian DPDP Act compliance gap)
3. **No IDOR Protection on User Profile**: Any authenticated user could potentially access another user's profile endpoint

### ✅ What We Implemented

**1. Password Log Leakage Prevention**

File: `backend/src/main/java/com/cms/module/auth/dto/LoginRequest.java`
```java
@Data
@ToString(exclude = "password")  // ← NEW: Password never appears in logs
public class LoginRequest {
    @NotBlank(message = "Username or email is required")
    private String usernameOrEmail;

    @NotBlank(message = "Password is required")
    private String password;
}
```

**2. GDPR Right-to-be-Forgotten Anonymization Endpoint**

File: `backend/src/main/java/com/cms/module/user/controller/UserController.java`
```java
@DeleteMapping("/{id}")
@PreAuthorize("hasRole('SUPER_ADMIN') or (hasRole('STUDENT') and @securityService.isOwner(#id))")
@Operation(summary = "Anonymize and delete personal data (GDPR Right-to-be-Forgotten)")
public ResponseEntity<Void> deleteUserData(@PathVariable Long id) {
    userService.anonymizeAndDeleteUserData(id);
    return ResponseEntity.noContent().build();
}
```

File: `backend/src/main/java/com/cms/module/user/service/impl/UserServiceImpl.java`
```java
@Override
@Transactional
public void anonymizeAndDeleteUserData(Long userId) {
    User user = userRepository.findById(userId)
            .orElseThrow(() -> new ResourceNotFoundException("User", "id", userId));

    user.setIsActive(false);
    user.setIsEmailVerified(false);
    user.setFirstName("REDACTED");
    user.setLastName("REDACTED");
    user.setEmail("anonymized_" + userId + "@cms.local");
    user.setPhone(null);
    user.setPasswordHash("$2a$10$ANONYMIZED_USER_ACCOUNT_CANNOT_LOGIN");
    userRepository.save(user);
}
```

> **Design Decision**: We anonymize instead of hard-deleting because foreign keys in `students`, `professors`, `enrollments`, `results`, and `payments` tables reference the `users` table. Deleting would cascade-destroy academic records. Anonymizing preserves institutional data integrity while eliminating all PII.

## Check 03 — Pre-Deploy Production Audit (ECC)

### 🔍 What We Audited
Reviewed HTTP response headers, brute-force defenses, and production error handling to ensure the application doesn't help attackers.

### 🐛 Vulnerabilities Found
1. **No browser security headers**: Missing `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, and `Content-Security-Policy` — leaving users vulnerable to clickjacking, MIME sniffing, and content injection
2. **No rate limiting**: Login endpoint had no brute-force protection, allowing unlimited credential stuffing
3. **Verbose error responses in production**: Stack traces and internal error details could leak in production

### ✅ What We Implemented

**1. HTTP Security Headers**

File: `backend/src/main/java/com/cms/config/SecurityConfig.java`
```java
http.headers(headers -> headers
    .frameOptions(frame -> frame.deny())                  // X-Frame-Options: DENY
    .contentTypeOptions(contentType -> {})                // X-Content-Type-Options: nosniff
    .httpStrictTransportSecurity(hsts -> hsts
        .includeSubDomains(true)
        .maxAgeInSeconds(31536000)                        // HSTS: 1 year
    )
    .contentSecurityPolicy(csp -> csp
        .policyDirectives("default-src 'self'; frame-ancestors 'none';")
    )
);
```

| Header | Value | Protection |
|--------|-------|------------|
| `X-Frame-Options` | `DENY` | Clickjacking |
| `X-Content-Type-Options` | `nosniff` | MIME-type sniffing |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | SSL stripping (HSTS) |
| `Content-Security-Policy` | `default-src 'self'; frame-ancestors 'none'` | XSS & content injection |

**2. Login Rate Limiting Filter**

File: `backend/src/main/java/com/cms/security/RateLimitingFilter.java`
```java
@Component
public class RateLimitingFilter extends OncePerRequestFilter {
    private static final int MAX_REQUESTS_PER_MINUTE = 5;
    private static final long WINDOW_MS = 60_000L;
    private final Map<String, RequestTracker> ipTracker = new ConcurrentHashMap<>();

    @Override
    protected void doFilterInternal(...) {
        // Targets: POST /api/v1/auth/login AND POST /api/v1/auth/refresh-token
        // Tracks per-IP request counts in a sliding 60-second window
        // Returns 429 Too Many Requests with ErrorCode.RATE_LIMIT_EXCEEDED
    }
}
```

- **Algorithm**: Sliding-window counter per client IP using `ConcurrentHashMap`
- **Limit**: 5 requests per minute per IP address
- **Response**: HTTP `429 Too Many Requests` with structured `ApiError` JSON body
- **IP Extraction**: Supports `X-Forwarded-For` header for reverse proxy deployments

**3. New Error Code**

File: `backend/src/main/java/com/cms/exception/ErrorCode.java`
```java

    // ... existing codes ...
    RATE_LIMIT_EXCEEDED  // ← NEW
}
```

## Check 04 — Deep Security Audit (Trail of Bits)

### 🔍 What We Audited
Reviewed complex business logic for exploitation — specifically payment processing, cross-user data access (IDOR), and authorization enforcement gaps.

### 🐛 Vulnerabilities Found

#### A. Insecure Direct Object Reference (IDOR)
Endpoints accepted `studentId` or `invoiceId` path parameters but only checked role membership, not resource ownership. A student with ID `42` could call `GET /api/v1/fees/student/99/summary` and see another student's fee records.

**Affected Controllers**:
- `StudentController` — `GET /{id}`, `GET /{id}/enrollments`
- `FeeController` — `GET /invoices/student/{studentId}`, `POST /payments`, `GET /payments/receipt/{receiptNumber}`, `GET /student/{studentId}/summary`
- `AttendanceController` — `GET /student/{studentId}`, `GET /student/{studentId}/stats`
- `ResultController` — `GET /students/{studentId}/examinations/{examinationId}`, `GET /students/{studentId}`

#### B. Missing Authorization Guards
Three controllers had **zero** `@PreAuthorize` annotations — any authenticated user (including students) could create/update/delete colleges, departments, and professors:
- `CollegeController` (7 endpoints unprotected)
- `DepartmentController` (9 endpoints unprotected)
- `ProfessorController` (8 endpoints unprotected)

#### C. Payment Logic Exploits
- No server-side check prevented a zero or negative payment amount (client `@Positive` annotation could be bypassed)
- No check prevented paying on an already-fully-paid invoice
- Discount amounts had no upper-bound validation (could exceed the fee structure amount)

### ✅ What We Implemented

**1. Ownership Verification Methods in SecurityService**

File: `backend/src/main/java/com/cms/security/SecurityService.java`
```java
// Resolves student → user relationship to verify the caller owns this student record
public boolean isStudentOwner(Long studentId) { ... }

// Resolves invoice → student → user chain to verify the caller owns this invoice
public boolean isInvoiceOwner(Long invoiceId) { ... }

// Resolves payment → invoice → student → user chain for receipt ownership
public boolean isPaymentOwner(String receiptNumber) { ... }
```

**2. IDOR-Protected Controller Annotations**

```java
// Before (VULNERABLE — any student can see any student's data):
@PreAuthorize("hasAnyRole('SUPER_ADMIN', 'ADMIN', 'HOD', 'STUDENT')")

// After (SECURE — students can only see their own data):
@PreAuthorize("hasAnyRole('SUPER_ADMIN', 'ADMIN', 'HOD') or (hasRole('STUDENT') and @securityService.isStudentOwner(#studentId))")
```

**3. Full RBAC Guards on Previously Unprotected Controllers**

| Controller | Read Endpoints | Write Endpoints |
|---|---|---|
| `CollegeController` | `SUPER_ADMIN, ADMIN, HOD, PROFESSOR, STUDENT` | `SUPER_ADMIN, ADMIN` |
| `DepartmentController` | `SUPER_ADMIN, ADMIN, HOD, PROFESSOR, STUDENT` | `SUPER_ADMIN, ADMIN` |
| `ProfessorController` | `SUPER_ADMIN, ADMIN, HOD, PROFESSOR, STUDENT` | Create/Delete: `SUPER_ADMIN, ADMIN`; Update: `+HOD` |

**4. Hardened Payment Logic**

File: `backend/src/main/java/com/cms/module/fee/service/impl/FeeServiceImpl.java`
```java
// NEW: Reject non-positive amounts (defense-in-depth beyond DTO validation)
if (request.getAmount() == null || request.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
    throw new BusinessException("Payment amount must be greater than zero");
}

// NEW: Reject payment on fully settled invoices
if (remainingAmount.compareTo(BigDecimal.ZERO) <= 0 || invoice.getStatus() == InvoiceStatus.PAID) {
    throw new BusinessException("Invoice is already fully paid");
}

// EXISTING (retained): Reject overpayment
if (request.getAmount().compareTo(remainingAmount) > 0) {
    throw new BusinessException("Payment amount exceeds remaining balance");
}
```

**5. Discount Validation**
```java
// NEW: Prevent negative discounts
if (request.getDiscountAmount().compareTo(BigDecimal.ZERO) < 0) {
    throw new BusinessException("Discount amount cannot be negative");
}
// NEW: Prevent discounts exceeding fee amount
if (request.getDiscountAmount().compareTo(feeStructure.getAmount()) > 0) {
    throw new BusinessException("Discount cannot exceed fee structure amount");
}
```

**6. DTO Validation Enhancement**

File: `backend/src/main/java/com/cms/module/fee/dto/request/FeeInvoiceRequest.java`
```java

private BigDecimal discountAmount;
```

## Check 05 — Attacker's Perspective Review (ECC)

### 🔍 What We Audited
Thought like an attacker — enumerated every exposed surface, privilege escalation path, token replay vector, and information leakage opportunity.

### 🐛 Vulnerabilities Found
1. **Refresh-token endpoint not rate-limited**: Only `/login` was protected; an attacker could brute-force refresh tokens at `/refresh-token`
2. **Production error responses leak internals**: Default Spring Boot error pages include stack traces, class names, and SQL fragments
3. **Actuator health details exposed**: Health endpoint shows internal database connection details, disk space, etc.

### ✅ What We Implemented

**1. Extended Rate Limiting to Refresh Token Endpoint**

File: `backend/src/main/java/com/cms/security/RateLimitingFilter.java`
```java
// Before: only /api/v1/auth/login
// After: both endpoints
boolean isAuthEndpoint = (
    "/api/v1/auth/login".equalsIgnoreCase(path) ||
    "/api/v1/auth/refresh-token".equalsIgnoreCase(path)
);
```

**2. Production Error Response Sanitization**

File: `backend/src/main/resources/application-prod.yml`
```yaml
server:
  error:
    include-message: never         # Don't leak exception messages
    include-binding-errors: never  # Don't leak validation internals
    include-stacktrace: never      # Don't leak stack traces
    include-exception: false       # Don't leak exception class names

management:
  endpoints:
    web:
      exposure:
        include: health,info       # Only health and info (no metrics, env, etc.)
  endpoint:
    health:
      show-details: never          # Don't leak DB/disk/component details
```

**3. Comprehensive Security Documentation**

File: `docs/SECURITY.md` — Updated with the full 5-check security audit matrix documenting vulnerabilities, attacker potential, and mitigations.
